## 已确认决策

| 项目       | 最终口径                                                                                |
| ---------- | --------------------------------------------------------------------------------------- |
| 默认登录   | 账号密码；邮箱验证码登录在账号登录内部切换，云端 Token 保持独立                         |
| 用户范围   | 仅已有且绑定邮箱的账号；不自动注册、不合并账号                                          |
| 邮箱       | 不限制邮箱域名；一个账号最多一个邮箱地址，一个邮箱地址只能绑定一个账号                  |
| 安全入口   | 用户页新增“账号与安全”；邮箱行显示“未绑定”或完整邮箱地址                                |
| 首次绑定   | 有效账号登录会话＋新邮箱验证码，不再次验证密码，不以登录方式限制绑定                    |
| 解绑       | 有效账号登录会话＋当前绑定邮箱验证码，不要求密码                                        |
| 更换邮箱   | 解绑后绑定新邮箱地址；不另建直接换绑流程                                                |
| 解绑效果   | 保留当前与其他设备会话；旧邮箱地址立即不能用于新登录，相关未完成挑战失效                |
| 收不到邮件 | 管理员核实账号归属后人工解绑，必须记录原因和审计                                        |
| 登录权限   | 与密码登录一致，复用原 accountId、AccountSession 和设备凭证                             |
| 验证码     | 6 位数字、5 分钟有效、60 秒重发；单挑战最多错 5 次，成功后一次性失效                    |
| 重发       | 成功重发使同用途旧码失效；失败或结果不明时不盲目重试、不清零累计失败限制                |
| 用途隔离   | 登录、绑定、解绑独立，验证码不得跨用途使用                                              |
| 发送体验   | 公开登录采用统一受理回执并直接倒计时；不披露单封投递状态、不增加解释弹窗                |
| 认证失败   | 登录对未绑定、停用、错误、过期及已消费挑战使用统一认证错误，不暴露账号存在性            |
| 邮箱匹配   | 去除首尾空白后，整地址小写作为查找和唯一键；保留已验证原地址用于投递，不折叠点号或 +tag |
| 发送渠道   | 标准 SMTP，由 Identity 发送；实际邮件服务、发件账号与额度在接入阶段确定                 |
| 邮件内容   | 中英双语纯文本；主题区分登录、绑定、解绑，正文含验证码、5 分钟有效期和非本人操作说明    |
| 投递体验   | 公开登录受理回执不代表投递；绑定/解绑由 SMTP 接受后倒计时，不宣称到达收件箱             |
| 发布       | 先后端再 App，使用少量后端配置开关灰度；保留解绑和人工处理能力                          |

## 最小架构

```text
App 页面 → accountEmailApi / accountAuth → Identity 账号接口
                                       → 现有 SQLite（绑定、挑战、限流、审计）
                                       → 一个 SMTP 发送函数 → 已配置的邮件服务

邮箱验证码登录成功 → 现有 AccountSession → 原恢复/刷新/退出/电脑目录链路
```

1. 页面只持有表单、提交、错误和倒计时等局部状态。邮箱绑定状态从 Identity 读取，不增加 MMKV/SQLite 镜像或全局 Provider。
2. `accountAuth` 负责登录态提交；账号安全 API 负责查询和绑定操作。复用现有请求与鉴权边界，不另建 HTTP 客户端或 Token 仓库。
3. 后端三个明确用途共用必要的验证码生成、发送、校验函数，业务 handler 直接完成各自操作。不建设通用认证、挑战编排或策略框架。
4. 用数据库唯一约束和事务完成竞争控制。保留绑定版本防止解绑/重绑后旧验证码复活；不扩展为事件溯源或版本管理系统。
5. SMTP 只需一个发送入口，测试替换该函数。配置一套服务器和发件身份，不预建 HTTP 邮件渠道、registry、工厂、故障转移或多服务商调度。
6. 邮件网络调用放在数据库事务之外；服务端发送冷却、额度、消费结果持久化。具体表结构由 T02 给出最小实现，不先引入 Redis、队列或后台任务平台。
7. 新抽象必须说明本任务中的实际复用点和减少的重复代码；只有“以后可能用到”不能成为增加抽象的理由。
8. 本次替代的重复状态、失效入口与无引用代码随改动删除；不得用兼容层保留两套绑定或邮箱验证码登录链路。

## 接口边界

下列路径已在两端落地，详见 [交付记录与定稿契约](IMPLEMENTATION.md) 和 Identity 的 `docs/account-email-api.md`；无接口别名。

| 接口                                             | 认证       | 请求 / 结果                                                |
| ------------------------------------------------ | ---------- | ---------------------------------------------------------- |
| GET `/api/auth/account/security`                 | 账号 Token | accountId、username、emailBinding（null 或 email/boundAt） |
| POST `/api/auth/account/email/challenges`        | 无         | email、requestId；返回挑战时间信息                         |
| POST `/api/auth/account/email/login`             | 无         | challengeId、code、deviceName；返回原 AccountSession       |
| POST `/api/auth/account/email/bind/challenges`   | 账号 Token | email、requestId；返回挑战时间信息                         |
| POST `/api/auth/account/email/bind`              | 账号 Token | challengeId、code；返回最新绑定摘要                        |
| POST `/api/auth/account/email/unbind/challenges` | 账号 Token | requestId；目标邮箱地址由服务端读取                        |
| POST `/api/auth/account/email/unbind`            | 账号 Token | challengeId、code；返回未绑定摘要                          |

挑战时间信息包含 `schemaVersion: 1`、challengeId、expiresAt、resendAvailableAt、serverTime。账号与安全摘要与认证会话分开；登录返回继续包含 schemaVersion、accountId、username、deviceId、deviceName、accessToken、accessTokenExpireAt、deviceToken。

绑定/解绑身份从认证会话取得，不接受客户端 accountId；绑定挑战还关联发起设备。未绑定或停用邮箱地址的公开发送请求不实际发送，仍提供一致的响应结构、冷却与外部时序，验证统一失败。不要用返回字段、HTTP 状态或处理时间暴露绑定关系。合法用户在已认证绑定流程中可以得到“邮箱地址不可用”等可操作提示，但不展示其他账号。

管理员解绑沿用 Identity 现有管理鉴权，只提供解绑及原因记录，不增加管理员代绑、批量导入或新权限平台。

## 邮箱与邮件规则

1. 首期支持常规 ASCII 邮箱地址，不设域名白名单。拒绝换行、控制字符、显示名称和多个收件人；只接受一个邮箱地址，不建设完整邮件地址语法兼容系统。
2. 保存投递地址和小写匹配键；前端输入与后端查询/唯一约束使用同一规则。大小写变体不能重复绑定、绕过冷却或重置额度。登录邮件发送到数据库中已验证的投递地址，不能改发到请求中的大小写变体。
3. 不按 Gmail 或其他厂商规则删除点号、去除 +tag 或合并别名。整地址匹配不区分大小写是产品约定；[RFC 5321](https://www.rfc-editor.org/rfc/rfc5321.html#section-2.3.11) 允许本地部分区分大小写，本产品不支持仅靠大小写区分的邮箱分别绑定不同账号。
4. 账号与安全、解绑页显示完整邮箱；完整地址只在已认证的账号安全摘要中返回。日志及审计继续脱敏，不记录邮件正文、验证码或 SMTP 认证信息。
5. SMTP 配置包括 host、port、TLS 方式、认证账号/凭证、发件地址和名称。使用 TLS 并验证证书；发件账号的发送权限及必要域名验证在上线前完成，不由 App 传发件人或品牌模板。
6. 一套固定中英双语纯文本正文按三个用途替换标题和用途词，不做 HTML、附件、登录链接、模板编辑器或品牌模板系统。
7. SMTP 接受只代表发送服务受理，不代表已进入收件箱。有效期以服务端 expiresAt 为准，垃圾邮件或晚到邮件不延长有效期；接受后启动冷却，未绑定邮箱的等价流程按相同时间规则返回。
8. 用户检查邮箱地址和垃圾邮件，60 秒后手动重发；接受新的同用途邮件后旧验证码失效，只接受最新验证码。SMTP 失败或结果不明不自动重试、不宣称已投递，保留之前仍有效的挑战；未确认的新挑战不得验证。公开登录按下述已确认回执决策返回，绑定/解绑明确反馈发送失败。

此处“接受”是 SMTP 最终 DATA 成功应答，不把建立连接或单个收件人被接受视为整封邮件发送成功。不新增投递回调、阅读追踪、自动重发或队列。

## 验收与执行纪律

- 两种账号登录使用同一个账号、设备凭证和权限；密码、云端 Token、QR 授权、电脑目录及聊天链路不被回归破坏。
- 覆盖验证码过期、重发、错码次数、累计限流、跨用途使用、并发绑定、重复消费及解绑后的旧码。
- 页面支持账户切换、请求取消、App 回前台重算倒计时和未知邮箱地址状态；查询失败不能显示为“未绑定”。
- 真实邮件、真机输入/粘贴及服务故障完成验证；mock、类型检查和导出不能替代真实验收。
- 首期发送额度与累计失败阈值是服务端配置。邮箱每小时 5 次、每日 10 次仅为建议初值，T01 结合服务商和用户规模定稿；重发不能绕过累计限制。
- App 沿用 NativeWind、主题 token、ScreenHeader/AppScreenFrame 等现有组件；只提取确实重复的少量表单行为，不建通用验证码页面引擎。
- 各仓库执行前读其 AGENTS.md，记录 Git 与临时状态。AI 不运行安装命令、不修改锁文件；默认不新增依赖。
- 更新实际落地的 `.doc/curated` 并运行 XGraph；按“未开始 / 进行中 / 已完成 / 阻塞 / 暂缓”同步总表和子任务。
- 每项完成记录改动、删除的冗余逻辑、验证结果、真实验收缺口和清理证据。清理未验证或真实验收未完成，不标整体完成。
