# T03 Identity 登录、绑定与解绑接口

[返回总览](../README.md)

状态：**已完成**。前置：[T02](T02-identity-email-storage.md)。交付后与 [T04](T04-app-api-session.md) 联调。

## 目标与范围

把验证码能力接入七个账号接口及最小人工解绑入口，复用现有鉴权和会话签发。邮箱从验证后的挑战取得，身份从服务端会话取得。

## 先读入口

- Identity：`backend/internal/app/server.go` 中账号登录、鉴权、会话签发、刷新和管理路由。
- `backend/internal/store/`、T01 契约及 T02 事务能力。
- `frontend/src/features/accounts/AccountsPage.jsx`，仅核实最小管理员解绑入口。

## 必须完成

1. GET security 查询真实绑定，返回 null 或完整邮箱摘要；查询失败不能伪装未绑定。校验有效账号会话与账号状态，不信任客户端身份字段。
2. 公开登录挑战按小写邮箱键查询有效绑定，邮件投递到数据库中已验证的原地址，不向请求中的大小写变体另行投递。未绑定/停用请求给出一致响应且不发送；校验约定格式和规范化键额度。
3. 邮箱验证码登录消费 login 挑战时重新查询当前绑定与 ACTIVE 状态；在同一事务中完成消费及既有会话创建。返回原 username/accountId 和原 AccountSession，保留 deviceName/deviceId 校验，不改权限或 token schema。
4. 已登录账号可请求 bind 挑战，不要求密码或最近密码登录证明。挑战关联原输入地址、小写键、发起账号和设备；提交时再次验证会话及账号未绑定，用唯一约束防止邮箱地址被并发占用。验证后的地址原样成为投递地址，消费与绑定写入原子完成。
5. unbind 挑战由服务端读取当前邮箱地址和绑定标识。提交时保证绑定仍是原记录，原子解绑、消费及失效旧绑定的相关挑战；不撤销当前或其他设备的既有会话。
6. 绑定、解绑成功返回最新摘要，App 不必靠本地猜状态。邮箱解绑后再次绑定也按新绑定处理，旧登录/解绑验证码不可复活。
7. 管理台账号详情增加最小“人工解绑”动作，沿用管理鉴权，要求确认及原因；同一解绑函数写审计并失效挑战。不得提供免验证代绑、任意邮箱地址修改或普通用户可达管理路由。
8. 通过两个后端启用配置控制邮箱验证码登录和新绑定；解绑与人工处理保持可用。使用现有配置，不新增远端功能配置服务。
9. 响应错误按 T01 分类，429 返回可用重试时间；普通日志对 email/code/otp/token 等脱敏。公开认证失败不通过 HTTP 状态或差异文案泄漏绑定关系。
10. 挑战时间信息反映 SMTP 接受后的服务端有效期与冷却，不返回或声称已到收件箱。发送失败/未知遵循统一契约，不自动重发；公开流程不能因是否绑定而暴露不同故障语义。

## 防止过度设计

复用 `createAccountAppLoginSession` 与现有认证入口；若支持事务只做必要参数/内部函数调整，不重写全部密码登录、刷新或退出。不新增认证工厂、策略插件、事件总线、管理员权限平台或资料管理框架。handler 可放专用小文件，但不把每个接口拆成无价值的层。

## 验收

- 七个接口与定稿契约一致；ACTIVE、Token、用途、账号、设备和绑定版本都由服务端校验。
- 两个账号竞争同一邮箱地址、同码并发登录、旧解绑码提交和解绑后旧登录码均不能绕过规则。
- bind 请求没有密码字段；已认证用户能首次绑定；解绑验证码只能发送到真实绑定邮箱地址。
- 解绑保留既有设备会话；管理员解绑需要管理身份、原因、确认和审计。
- 原密码登录、QR 挑战、refresh/logout/me 与管理台既有能力回归通过。
