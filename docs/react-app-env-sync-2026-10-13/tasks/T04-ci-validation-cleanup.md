## 目标与范围

复用前三项的同一入口，完成手动触发的构建/OTA、发布记录和真实验收。CI 是脚本调用层，不实现第二套配置、目标解析或发布平台。

## 先读入口

- 本目录 T01–T03 的实际交付记录、[EAS 配置](../../../eas.json)、[IPA 提交入口](../../../scripts/submit-ios-ipa.js)、当前 App CI（若存在）。
- react-app-env 的 .github/workflows/release.yml、制品/consumer 校验与版本命名规则；核对当前 app-ref 默认 main 的浮动输入，不将其视为固定发布版本。
- 六个目标的平台注册、签名、真实服务配置和构建/更新状态；缺材料明确记录，不输出真实凭据。

## 必须完成

1. App 增加手动触发 CI，输入至少包含操作（构建/OTA）、brand、environment、platform、固定 App/env ref 与制品身份。tag 解析到 commit 后记录；不将浮动 main/latest 作为不可追溯的实际发布输入。
2. CI 调用 T03 装配入口和 T01/T02 的既有校验；私有配置在任务自有目录物化，制品/manifest进入临时 App 上下文。失败、取消和命令退出均清理自有私有材料，不把真实配置/Token 上传成调试附件。
3. 只发布明确目标的构建或同名 OTA channel/branch；核对 runtimeVersion/应用标识。共用一个 EAS 项目不发布共享频道，不跨品牌/环境复用更新。
4. 保存一份简单发布记录：App/env commit、schema/artifactVersion、制品 SHA-256、brand/environment/platform、App version、构建号、channel/runtimeVersion、EAS build/update ID 与结果。记录中不含 Token，不新增发布数据库或 registry 服务。
5. 商店提交选择明确 build ID/IPA及对应应用记录；删除按 --latest 猜品牌的调用。构建、OTA 和商店提交各自记录执行结果，不把生成 IPA 当成提交成功。
6. 回滚使用历史记录中的固定 App/env组合或该目标既有兼容更新；禁止跨目标 republish。env 制品不能作为“同名版本的可变文件”被原地替换。
7. 整理 README、对应 curated modules/flows/tasks/rules 与索引；移除本次已替代且确认无引用的脚本、配置和测试。不修改其他计划的状态，不重构无关业务。

## 防止过度设计

采用手动 workflow＋现有 CLI 即可；不增加合并/tag 自动生产发布、灰度平台、多层流水线 DSL、动态矩阵调度服务、长期 secret 工作区、制品下载服务或通用回滚引擎。六个静态目标使用明确矩阵，不为未来品牌预建插件体系。

## 集成验收矩阵

| 场景                      | 必须验证的结果                                                                             |
| ------------------------- | ------------------------------------------------------------------------------------------ |
| 六目标 × Android/iOS 配置 | 安装标识唯一；原生、JS、服务地址、更新 URL/channel/runtime 一致                            |
| 真机安装                  | 两品牌和同品牌多环境可并排安装，名称/图标/启动正确，本地数据不串                           |
| 本地调试与 Web            | 默认 ZenMind/development 可用；显式目标正确；Web 预览/导出使用相同配置                     |
| 正式构建                  | 固定版本的制品实际进入远端构建，安装后加载真实默认源并完成目录和一轮对话                   |
| 分目标 OTA                | 对一个品牌/环境更新配置或 JS，仅该目标改变；另一品牌、其他环境保持不变                     |
| 错配                      | 摘要不符、缺配置、example 正式使用、壳/Bundle错配、错误 channel/runtime 在使用或发布前失败 |
| 账号配置变化              | 不向新 Identity/Hub 发送旧凭据；重新登录可用，未变化时正常恢复                             |
| 云端凭据与缓存            | 手动/配置 Token、主动退出、换凭据验证、迟到结果及旧 outbox 隔离符合 T03                    |
| 失败与清理                | 物化失败、构建失败、命令中断后恢复临时状态，不覆盖用户配置或留下私有材料                   |

执行项目已有 lint、类型检查、相关行为测试和生产导出；静态矩阵可以一次遍历，不需要重复创建测试工程。真实安装/服务/OTA 各自记录目标、版本、步骤和结果，未执行标为未执行。Expo export 或 mock 通过不能替代原生安装包和真实验证。

外部账号/签名/服务材料不足时记录准确缺口及接手动作，完成其余可独立验证内容；对应真实验收与总计划保持未完成，不为消除阻塞增加模拟服务或兼容 fallback。

## 完成与清理门槛

- 前三项有实际实施证据，T04 的必要真实矩阵通过，所有子任务与总览状态一致。
- 清理全部任务自有临时上下文、真实配置物化副本和日志中的私有材料；保留预先存在的 env/dist/native/cache 和用户改动。
- 审计 Git status/diff、变更过的配置和生成目录；临时 Git/env/proxy/hook 状态恢复原状，只保留有意交付的代码/文档。
- 运行 git diff --check、xgraph index、xgraph sync、xgraph status，确认索引及规则反映实际实现。
- 无旧共享身份/全品牌选择路径、旧地址覆盖、重复准备入口和失效测试；仍有调用且无关的代码不能顺手删除。
- 清理无法完成或验证时，列出准确残留及修复命令，任务保持未完成。
