## 执行顺序与依赖

以下顺序只适用于 T00 纳入的范围及其必要前置；未纳入的任务不因列在某阶段而自动实施。

1. **A：冻结协议。**先完成 [T00 冻结协议基线与同步范围](tasks/T00-protocol-baseline.md)，逐项明确本期范围、接口支持、兼容默认值和样本，记录实际执行版本。T02 输出面板、T14 队列及持久化/自动转换、T23 复制与搜索均明确最小范围；T10 两部分分别决定。
2. **B1：公共前置。**完成 T05 owner、T13 时间契约、T06 模型配置，再推进 T01 工具状态、T07 已读、T08 续聊和 T12 能力。
3. **B2：数据消费。**在对应前置完成后推进本期纳入的 T02 输出、T03 流失败、T04 awaiting、T09 VIEW、T10 周期协议修复与 T11 重试。T09 依赖 T04，不能只先加表单入口。
4. **B3：时序专项。**按 T28 → T29 验证快照和有界恢复；T30 同时依赖 T01、T05、T28。对已经满足的保护补证据即可。
5. **C：选择能力。**只启动 T00 纳入本期的可选能力，按任务头部依赖执行，包括单独纳入的 T10 主动压缩。例如 T25 BTW 要等 T18 引用与 T29 恢复完成；T20 图片展示不依赖 T02 输出面板。
6. **D：联合交付。**T31 根据 T00 的范围决定验收已纳入任务、任务部分及其必要前置，覆盖基础任务产物与实际影响的跨任务组合。暂缓项写明理由；验证专项可凭“不需要代码变更”的证据关闭。

不同任务可以在依赖满足后分别推进，但 `chatSyncService`、`chatApi`、`timelineReducer`、`chatRepository` 是共享热点，实施时按文件和协议契约协调，避免各自产生第二套 owner、运行态或时间解析。

建议每次只实施一个任务或一组不可分割的前后置任务，完成后同步总览状态与子任务执行记录，再进入下一批。

## 实施边界

- **绝对禁止过度设计。**新增代码必须对应已确认的需求或缺陷，并采用满足验收的最简单方案；不为未来需求预建框架，不因 WebClient 更复杂就照搬，不为单个功能建立第二套状态。身份隔离、幂等、内存上限与真实终态属于必要正确性要求，不能省略。
- 优先修改现有入口；只有实际重复才提取公共代码，只有实际恢复需求才新增持久化，只有旧数据确实不兼容才迁移。避免新增通用状态机、动作路由、模式、能力、导出或会话引擎；这些计划不授权建设公共基础框架。
- 页面与组件消费 controller/service 产物；API 走 core 服务，实时业务写入走 `chatSyncService` / `chatRepository`。页面不得直接访问 SQLite、MMKV 或 WebSocket。
- 联网与能力校验通过后，先保存消息并提交一次 query；requestId 使用本地消息 ID。有效服务端事件确认后标记已发送；未确认断线记为失败，重连只回读详情并 attach 已确认 Run，手动重发先核对历史。
- reducer/projector 保持数据投影职责；资源请求、提交、复制、分享和恢复操作放在对应 service/controller，不在 replay 中执行副作用。
- 每个异步操作明确 source namespace、connection、owner、chatId 和 runId 的适用范围，防止切换账号、Profile、Agent/Team 后旧结果回写。
- transport done、detach、本地停止展示、interrupt 接受与服务端业务终态分别处理。关闭单个功能不得停止共享 socket 或移除其他 feature 的监听。
- 区分 missing、null、未知结果、实时事件、权威详情和旧页历史；历史事件不能无条件覆盖当前 awaiting、read state 或 canContinue。
- 联网与能力校验通过后，先保存消息并提交一次 query；requestId 使用本地消息 ID。有效服务端事件确认后标记已发送；未确认断线记为失败，重连只回读详情并 attach 已确认 Run，手动重发先核对历史。
- UI 使用现有主题、NativeWind 和共享组件；平台差异应显式降级，不把 Web/Desktop bridge 直接搬到 Native。
- 新增或调整依赖只修改 `package.json`，不运行安装命令、不改 lock 文件；需要安装时由用户手动执行。
- 任务改变公共入口、职责、运行链路或规则时，同步 `.doc/curated` 并执行 `xgraph index`、`xgraph status` 和仓库要求的 `xgraph sync` / finish 流程。

## 状态与完成标准

使用 `[ ] 未开始`、`[-] 进行中`、`[!] 阻塞`、`[x] 已完成`，同时更新总览和子任务头部。范围字段单独记录“纳入本期 / 暂缓 / 已具备待验证”；暂缓不等于完成或阻塞。

完成任务必须同时满足：明确范围内的验收项、可复查的代码/样本/测试证据、必要的持久化兼容和 XGraph 更新，以及临时状态清理。新增抽象、状态和持久化均须在现有设计取舍记录中说明对应的实际需求；不增加独立审批或管理流程。验证专项允许以“不需要代码变更”结束，但必须记录具体测试和结论。部分能力暂缓时记录各部分结论，不把暂缓部分标为已完成，T31 只验收已纳入部分。

子任务中的执行记录用于填写实际起止日期、提交/PR、后端版本、变更文件、测试结果、迁移/回滚、残留风险和清理结果。实现时若分拆或合并任务，保持旧 ID 的引用关系并更新所有依赖。
