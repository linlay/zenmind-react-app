推荐实现方案

核心原则：移动端保留现有 AppIcon 业务语义入口，只替换底层 glyph 数据与 usage 映射；页面、聊天组件、附件组件都不直接选择 SVG path 或底层 glyph。

推荐范围：首批只引入对话列表和详情页实际需要的 24 个 Material glyph，而不是一次性搬运 PC 全 102 个 symbol。这样包体更小、审查面更窄，也更符合当前任务边界。

层级 职责 建议文件 性能/优雅性约束
业务语义层 把 chatDetail.back、composer.send、timeline.copy 这类业务 usage 映射到 glyph。 src/shared/icons/registries/appIconUsages.ts 唯一允许业务选择图标的地方；screen 和 feature component 不写 glyph 名。
glyph 注册层 声明当前 RN 可用 glyph 名，包含既有 RN glyph 与首批 Material glyph。 src/shared/icons/registries/appIconRegistry.ts 纯静态对象 + TypeScript union；不做运行时解析。
path 数据层 保存 Material path 数据和 viewBox。 src/shared/icons/registries/appIconGlyphPaths.ts 一份 path 数据，多处复用；禁止每个图标一个组件文件，避免代码膨胀。
渲染层 用统一 renderer 把 path 数据渲染为 react-native-svg。 src/shared/visual/AppLineIcon.tsx 或新 src/shared/icons/AppGlyphIcon.tsx 组件 memo，render 内只做一次 O(1) 查表；不使用 SvgXml、不解析远端 SVG、不动态 import。
聊天组件层 继续消费 AppIcon / AppIconButton。 ChatHomeScreen、ChatDetailHeader、Composer、ChatTimelineList 等 只替换 usage 或补充少量新 usage；不引入局部 icon map。

推荐数据结构

把当前 AppLineIcon 中“名字 → path”的分支改成静态定义表，支持 Material 的 0 0 960 960 与旧 RN 的 0 0 1024 1024 并存。

type AppIconPathNode = {
  d: string;
  fillRule?: 'evenodd' | 'nonzero';
};

type AppIconGlyphDefinition = {
  viewBox: '0 0 960 960' | '0 0 1024 1024' | '0 0 24 24';
  paths: readonly AppIconPathNode[];
};

export const appIconGlyphPaths = {
  content_copy: {
    viewBox: '0 0 960 960',
    paths: [{ d: '...' }]
  },
  arrow_upward: {
    viewBox: '0 0 960 960',
    paths: [{ d: '...' }]
  }
} as const satisfies Record<AppIconGlyphName, AppIconGlyphDefinition>;

这样新增图标只改一处数据表；渲染逻辑不随图标数量增长而膨胀。

高性能约束

约束 具体做法 要避免的写法
零运行时解析 PC SVG path 在提交前转成 RN 静态 path 数据。 SvgXml、运行时读取 .svg、运行时解析 sprite。
O(1) 查表 AppIcon 查 usage，renderer 查 glyph definition，均为静态对象索引。 在列表 item render 中遍历图标数组、动态拼装复杂对象。
不重复定义 path 同一 glyph 只在 appIconGlyphPaths 出现一次。 copy、content_copy 各放一份相同 path；每个业务组件各写一份 SVG。
少量新 usage，语义清晰 动态状态用两个明确 usage，例如 runtime.wrapEnabled / runtime.wrapDisabled。 给 AppIcon 增加业务判断，或在组件里传裸 glyph 名。
保持列表稳定 已有 AppIcon、AppLineIcon 继续 memo；高频 row 不创建临时 style/glyph map。 在 ChatRow、timeline row 内构造 icon registry 或 path 对象。
包体受控 首批只加入聊天主链路 24 个 glyph；第二阶段再补操作菜单和附件扩展。 为了“看起来统一”一次性搬入 PC 全量 102 个 symbol。

去冗余规则

  • 不新建第二套公共图标组件。最终对外仍只有 AppIcon / AppIconButton，底层 renderer 可以重构，但调用边界不扩散。
  • 不做全局 alias 层。迁移过的 usage 直接映射到 Material 名；旧 RN glyph 只为未迁移页面保留，不让 copy 永久 alias 到 content_copy。
  • 不把 PC 文件直接拷进 RN 运行时。PC 的 sprite.svg 是输入资料，RN 只保留经过整理的 path registry。
  • 不让 feature 组件 import AppLineIcon。ChatAttachmentStrip 改为 AppIcon usage，这是本轮清理的重点。
  • 不为单个页面造局部 icon map。附件类型、runtime 类型、composer 状态都回到 shared usage 或 feature 内纯函数返回 usage。

落地步骤

  1. 提取首批 path。从 PC sprite.svg 取第一阶段 24 个 glyph，整理为 appIconGlyphPaths 静态表，保留 path 原始精度，不手改曲线。
  2. 泛化 renderer。让 AppLineIcon 支持 viewBox + path array；旧 outline fallback 如 history 可暂时保留，但新增 Material glyph 一律走同一 path table。
  3. 更新 usage 映射。在 appIconUsages 中把聊天主链路 usage 映射到 edit_square、content_copy、reply、person 等 Material 名。
  4. 清理直接调用。ChatAttachmentStrip 改为 AppIcon，新增附件类型 usage，例如 attachment.filePdf、attachment.fileSheet、attachment.fileArchive。
  5. 处理动态状态。新增明确 usage，例如 runtime.wrapEnabled / runtime.wrapDisabled、timeline.reaskCurrent / timeline.reaskNewConversation，不把状态判断塞进 AppIcon。
  6. 加校验测试。新增脚本测试：每个 appIconUsages[usage].glyph 都存在于 appIconRegistry 和 appIconGlyphPaths；聊天目录下不得直接 import AppLineIcon。
  7. 视觉验收。跑 typecheck 后用当前模拟数据检查 Chat 首页、Chat 详情、composer 展开/收起、timeline runtime row、附件条和深色主题。

需要确认

决策点：首批是否只引入聊天主链路 24 个 Material glyph？

我的建议是只做首批子集。这样性能、包体、审查成本都更稳；PC 全 102 个 symbol 可作为后续“全局图标统一”任务，由脚本生成并单独验收。
